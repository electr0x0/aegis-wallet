# 05 — Security self-assessment

This assessment covers the AegisWallet prototype as it stands in this repository. The prototype runs on Base Sepolia only, with one local operator and one Node process. It describes what each control does, what it does not do, and how the controls were verified. Architecture and algorithms are in [01 — Technical documentation](01_TECHNICAL_DOCUMENTATION.md).

## 1. Trust boundary

| Component                       | Trust assumption                                                                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Operator at the dashboard       | Trusted. The only human authority; approves Tier 2 proposals                                                                          |
| Server process and `.env.local` | Trusted in this prototype. Holds the agent key and, for now, the owner key (see risk R2)                                              |
| LLM provider and model output   | Untrusted. Can only select typed tools whose arguments are validated; cannot sign or approve                                          |
| Prompt text                     | Untrusted. Screened by heuristics, and bounded by policy whatever it says                                                             |
| RPC endpoint                    | Trusted for availability and simulation results; the chain ID is checked. The AgentGuard limits do not depend on the RPC being honest |
| AgentGuard contract             | The enforcement point of last resort. Its owner key is the root of authority                                                          |

Keys never leave the server. API responses, the dashboard and evidence exports contain only public addresses. There is no browser-side key and no wallet extension.

## 2. Permission-tier implementation

### Operator PIN step-up and local accounts

Tier 2 approval and every policy save require a fresh six-digit operator PIN verified on the server inside the mutation mutex. Successful checks record `TIER_2_AUTH_SUCCESS`; incorrect, missing or locked PINs record `TIER_2_AUTH_FAILED`. The PIN is consumed with the specific request; no reusable elevation token is returned. Approval still rechecks the stored account-bound action, latest policy, chain ID, simulation and guard. Five failed attempts cause a persistent five-minute lockout. A failed check leaves the proposal and policy unchanged.

The master PIN **884210** is intentionally public, with a judge quick-fill button. It is a demonstration of the step-up flow and provides no meaningful secrecy against a knowledgeable local attacker. Custom wallets use their own PIN, with no master-PIN fallback. The master is default-active for trusted local requests without a cookie. Roles are account metadata, not production tenant RBAC. Loopback and same-origin restrictions remain essential.

New account keys are encrypted at rest with AES-256-GCM. scrypt derives the encryption key from the PIN, per-account salt and a separate server salt file. The authentication tag covers identity-bound additional data; PIN verification uses a constant-time HMAC comparison. A six-digit PIN has limited entropy: possession of both account storage and the server salt enables offline guessing despite scrypt. The server holds an unlocked key in memory for the 30-minute session, and server compromise bypasses this control. There is no HSM, WebAuthn, MFA, hardware-backed PIN verification, or independent owner device. The requested master status `HSM_ENV_ISOLATED` refers only to an environment-held software key.

Sessions use opaque random tokens in HttpOnly, SameSite=Strict cookies, Secure on HTTPS. Custom sessions expire or become locked after a restart. Account switching binds the signer, guard mode, policy, proposals and budget through AsyncLocalStorage; stale-account API mutations are rejected. New accounts use EOA mode and have no on-chain session guard. The master retains its existing guard; provisioning never claims that a new EOA has an on-chain session key. The master display name “Pre-Funded” is a preset label; live balances may be zero or unavailable.

### 2.1 Tier × conditions × who signs

| Tier                           | Conditions                                                                                                                                                                                                                                                                                                                                      | Signer, EOA mode (no guard)     | Signer, guard mode                                                                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tier 0 — Observe**           | Read-only tools: `get_wallet_portfolio`, `audit_contract_address`. No write path                                                                                                                                                                                                                                                                | Nobody                          | Nobody                                                                                                                                                                                          |
| **Tier 1 — Autonomous**        | Every hard check passes, and all of the following hold:<br>• recipient whitelisted<br>• value ≤ single-transaction cap ($20 default)<br>• rolling 24-hour Tier 1 spend plus value ≤ $50 default<br>• reserve runway after the transfer ≥ floor (transfers only)<br>• "always ask" off<br>• in guard mode, the guard pre-flight accepts the call | Agent key signs the transaction | Session key signs `guard.execute`. The contract re-checks expiry, allowlists and per-asset caps on-chain                                                                                        |
| **Tier 2 — Human in the loop** | Every hard check passes, but at least one soft condition above fails. | **BLOCKED**                    | Any of:<br>• blacklisted recipient<br>• injection language with a non-whitelisted recipient<br>• a token contract as recipient<br>• non-positive or non-finite value<br>• simulation failure, including wrong chain<br>• gas price above the ceiling<br>• guard pre-flight rejection<br>• owner-approval failure                                | Nobody                          | Nobody                                                                                                                                                                                          |

Approval cannot override a hard block. On approval, the stored action is re-evaluated against the current policy and a fresh simulation, and then, in guard mode, against the contract itself. Swaps, yield deposits, staking and bridging are refused before any parsing or planning.

In EOA mode Tier 2 is weaker than in guard mode. The approval is a local UI confirmation followed by a signature from the same agent key. Guard mode turns approval into a cryptographic authorisation that the chain verifies.

### 2.2 Defence in depth

| Attacker controls                                | Layer 1 (policy) | Layer 2 (simulation) | Layer 3 (AgentGuard) | Outcome                                                            |
| ------------------------------------------------ | ---------------- | -------------------- | -------------------- | ------------------------------------------------------------------ |
| Prompt text                                      | Applies          | Applies              | Applies              | Bounded by Tier 1 caps; anything larger waits for a human          |
| LLM output                                       | Applies          | Applies              | Applies              | Same; the model cannot sign, approve or replace the prompt         |
| Agent logic, or the off-chain policy file        | Bypassed         | Bypassed             | Applies              | Bounded by on-chain caps to allowlisted recipients and call shapes |
| Session (agent) key                              | Bypassed         | Bypassed             | Applies              | Same; demonstrated by `pnpm guard:attack` (section 4)              |
| Owner key, or the whole server in this prototype | Bypassed         | Bypassed             | Bypassed             | Full loss of guarded funds (R2)                                    |

## 4. Attack demonstration: compromised key against AgentGuard

`scripts/attack-demo.ts` plays an attacker who already holds the real session key and skips every off-chain defence: the policy engine, the injection filter and human approval. It calls `AgentGuard.execute` directly, so only the contract stands between the attacker and the funds.

```powershell
pnpm guard:attack              # simulates three attacks; nothing is sent
pnpm guard:attack --broadcast  # also sends attack (a), so the on-chain revert is BaseScan evidence
```

| Attack                  | Call                                                  | Expected guard error (from the contract's check order) |
| ----------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| (a) Drain USDC          | `USDC.transfer(0x1337…1337, entire guard balance)`    | `RecipientNotAllowed`                                  |
| (b) Oversized ETH       | Send 0.05 ETH to the vault (cap 0.01 per transaction) | `PerTxLimitExceeded`                                   |
| (c) Unlimited allowance | `USDC.approve(0x1337…1337, max)`                      | `SelectorNotAllowed`                                   |

The script exits with a non-zero code if any attack is not blocked in simulation, and it refuses to broadcast unless attack (a) was blocked. With `--broadcast`, it sends attack (a) with a fixed gas limit, bypassing gas estimation, which would refuse a known revert. It confirms the receipt status is `reverted` and records the attempt in the sealed ledger as `REVERTED_BY_GUARD`. If the session has expired, every attack reverts with `SessionExpired`; run `pnpm guard:deploy --renew` first so the demo exercises the limits rather than expiry.

Evidence for the broadcast revert: see the Deliverable 06 evidence export (`data/audit_log.json` → dashboard Export).

### 4.1 Emergency stop and recovery

The operator's kill switch is the human-intervention control for an AI agent that moves funds, in line with NFRA guidance 金发〔2026〕8号 on human supervision of high-risk AI.

```powershell
pnpm guard:deploy --revoke   # emergency stop: the owner revokes the session key on-chain
pnpm guard:attack            # optional check: all three attacks now fail with NotSessionKey
pnpm guard:deploy --renew    # recovery: restore the session for SESSION_HOURS (default 24)
```

- **Stop.** `revokeSession` sets the session key and its expiry to zero. From then on `execute` and `executeApproved` revert with `NotSessionKey` for the agent key. The session-key check runs before the expiry check, so the error is `NotSessionKey`, not `SessionExpired`. The dashboard's guard pre-flight then blocks Tier 1 writes, and a Tier 2 approval fails the same pre-flight, so nothing is broadcast. Owner approvals signed but not yet submitted are unusable while the session is revoked, because only the session key can submit them. They become valid again after a restore, until their 10-minute deadline.
- **Who sends it.** The script prefers the owner EOA (`VAULT_PRIVATE_KEY`) sending `revokeSession` directly, because that does not depend on the agent key being stopped. If the owner has no gas, the owner signs the call and the session key relays it through `executeApproved`, the same way `--renew` works. Before anything is sent, the script checks that the vault key is the on-chain owner and simulates the call from the paying address. It refuses if the simulation fails or the session is already revoked. The confirmed transaction is recorded in the sealed ledger as `SETUP_GUARD_REVOKE`.
- **Recovery.** After a revoke the session key is the zero address, so nothing can be relayed. A relayed renewal cannot undo a revoke. Only a transaction the owner EOA sends itself, `setSession(key, expiry)`, restores the session, so the owner needs its own gas. `--renew` detects this and takes that path. After a stop for a suspected compromise, wait at least 10 minutes before `--renew`, so that any approval signed before the stop has expired. The restore keeps earlier state: the day's spend and used nonces carry over. If the owner cannot pay, it refuses and prints the owner address and the ETH it needs. One admin call costs about 28,000 gas (revoke) or 46,000 gas (renew after a revoke), well under 0.00001 ETH at current Base Sepolia fees. `--revoke` prints a warning when the owner holds too little gas to renew afterwards.
- **Ledger.** The script is a second ledger writer (R13). Stop `pnpm dev` first when you can, which also halts the off-chain agent. The on-chain revoke does not depend on it.
- **Funding the owner.** The owner is the vault, which is an allowlisted recipient, so the agent can send it a little ETH through the normal policy path while the session is still live. After a revoke the agent can no longer reach the guard. The owner then has to be funded from outside, for example from a faucet.
- **What it does not stop.** The agent EOA's own gas ETH is not held by the guard, and a revoke does not move it. Funds stay in the guard, and the owner can still move them with `ownerExecute`, paying its own gas.

- **Reserve-runway calculation, `explainDecision` rationales, the intent router and demo parser, the LLM planner loop, and the bytecode scanner.**

None of this is a formal audit, and none of the automated tests proves live testnet execution. Real evidence exists only after funding and confirmation on Base Sepolia.

Method: (a) sends each prompt through the real API route, `runIntent` and the deterministic parser, and a prompt handed to the planner gets a stub model that makes no tool call; (b) skips the router and drives the real planner loop with a compromised model that emits the attacker's tool calls, with attacker-chosen arguments, and then echoes its whole context. Both use the committed `data/policy.json` and real transaction encoding on a mocked chain where every simulation passes and the wallet holds 10,000 USDC, so only policy can stop an attack; throwaway keys, PINs, API keys and a session token are searched for in every API response, reply, planner request and ledger file.

"Value moved autonomously" counts Tier 1 broadcasts to a non-whitelisted recipient, above a cap, or with a forbidden selector. The only in-mandate broadcasts were in the structuring case (IT-11, both models): two 19 USDC transfers to the whitelisted vault, after which the $50 rolling budget held the rest. Before the router fixes in the same commit (section 3.1 of the technical documentation), "1,5 USDC" and "Do not send 5 USDC" each sent 5 USDC to the vault autonomously, and all 14 extraction requests reached the planner instead of being refused.

## 6. Evidence handling

Every attempted write records:

- time and the original intent
- tier, status and risk score
- simulation result and USD reference value
- the deterministic rationale and the policy hash
- any transaction hash

Each entry is then sealed into the hash chain. Status semantics:

| Status                           | Meaning                                                                                      |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| `BROADCASTING` without a hash    | Submission outcome unknown. Inspect the wallet's history before any retry                    |
| `SUBMITTED` with a hash          | Sent; the receipt may still be pending if polling timed out                                  |
| `CONFIRMED`                      | A successful receipt was observed                                                            |
| `REVERTED`                       | Mined but reverted                                                                           |
| `REVERTED_BY_GUARD`              | Attack-demo transaction reverted by AgentGuard                                               |
| `BLOCKED`, `REJECTED`, `DRY_RUN` | Nothing was signed                                                                           |
| `AWAITING_HITL_APPROVAL`         | Tier 2 proposal created                                                                      |
| `COMPLETED`                      | A Tier 0 portfolio read, an account provisioning event, or a policy change (`POLICY_UPDATE`) |
| `SETUP` tier                     | Operator guard deployment, funding, renewal or emergency stop                                |

The dashboard Export writes `aegis-evidence.json` (the full sealed entries) and `aegis-evidence.md` (a readable summary with BaseScan links). Neither ever invents proof of execution. The hashes for this submission: see the Deliverable 06 evidence export (`data/audit_log.json` → dashboard Export).

## 8. Path to production

1. Move the owner key off the server, to a hardware wallet or passkey (WebAuthn), and have the operator sign approvals on that device using EIP-712 typed data.
2. Replace the fixed reference price with a manipulation-resistant oracle, and move USD policy math to integer base units.
3. Port AgentGuard to a standard modular account (ERC-4337 with an ERC-7579 session-key validator) for bundler and paymaster support. Extend the in-process contract suite with fuzz and invariant testing, and commission an external audit.
4. Anchor the latest ledger hash externally, for example on-chain or in a write-once store, and move the ledger to a transactional database for multi-process operation.
5. Add operator authentication and MFA before any non-local deployment.
6. Deploy only in a jurisdiction that licenses the activity, with licensed assets and KYC and AML controls (section 7.5).
7. Give the owner key its own gas budget, or a paymaster. After an emergency stop it is the only key that can restore the session, and in this prototype it holds no ETH unless the operator funds it. A production stop could also add a pause that keeps the session key, so that recovery does not need a new `setSession`.
